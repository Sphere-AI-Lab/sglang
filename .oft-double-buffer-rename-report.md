# --peft-double-buffer -> --oft-double-buffer rename report

## Precedent read

Read `git show a2439d7fcd -- python/sglang/srt/peft/config.py` (the
`--peft-target-modules` -> `--oft-target-modules` rename) and
`git show 7b75dc8a06 -- python/sglang/srt/peft/config.py` (the follow-up fix
for the read-only-`ServerArgs` crash: the deprecation-copy must resolve into
a LOCAL variable and publish via `server_args._late_resolution(...)`, never
`server_args.<field> = ...` directly, since `ServerArgs.__setattr__` raises
`AttributeError` for any bare field write once `__post_init__` sets
`_declarations_materialized`, which is always true by the time
`validate_peft_args` runs at a real server launch). Also read
`7b75dc8a06`'s test diff for the exact real-`ServerArgs` regression-test
construction pattern (`ServerArgs.__new__(ServerArgs)` + `object.__setattr__`
per field + `_declarations_materialized = True`).

## Changes, file by file

### `python/sglang/srt/peft/config.py`
- Renamed the canonical `PEFTArgs` field `peft_double_buffer` -> `oft_double_buffer`.
- Re-added `peft_double_buffer: A[bool, NS("lora")] = False` as a deprecated,
  input-only field (mirrors how `peft_target_modules` was kept).
- `register_peft_args`: added `--oft-double-buffer` (canonical, same
  `action="store_true"`/help text as the old flag) and kept
  `--peft-double-buffer` (deprecated alias, help text points at the new flag),
  in that order (canonical first), mirroring the target-modules registration
  order.
- `validate_peft_args`: added the OR-merge deprecation logic immediately
  after the existing `--peft-target-modules`/`--oft-target-modules` alias
  block (same kind of concern, same location):
  ```python
  oft_double_buffer = server_args.oft_double_buffer or server_args.peft_double_buffer
  if server_args.peft_double_buffer:
      logger.warning(
          "--peft-double-buffer is deprecated; use --oft-double-buffer instead."
      )
  ```
  Resolved into a local (not written to `server_args.oft_double_buffer`
  directly) for the exact reason `7b75dc8a06` documents. Unlike the
  string-list target-modules alias, a boolean has no "conflicting values"
  case -- OR-merge is the only sensible semantics (either flag being True
  means it's on), so there is no `raise ValueError` branch here.
- Updated the `if server_args.peft_double_buffer:` usage (the
  `max_ofts_per_batch >= 3` double-buffer-sizing guard) to read the local
  `if oft_double_buffer:` instead.
- Added `oft_double_buffer=oft_double_buffer` to the existing end-of-function
  `server_args._late_resolution("validate_peft_args", ...)` call (alongside
  `oft_target_modules=oft_target_modules`), so the resolved value survives
  once and only once, published through the one legal write path.

### `python/sglang/srt/oft/oft_manager.py`
- `OFTManager.__init__`: renamed `self.peft_double_buffer` ->
  `self.oft_double_buffer`, now reading from the now-canonical, already-
  resolved `server_args.oft_double_buffer`. Updated the adjacent comment
  from `PEFTArgs.peft_double_buffer` to `PEFTArgs.oft_double_buffer`.
- Updated the two other usages: `if self.oft_double_buffer:` (double-buffer
  staging-from-active seed) and `double_buffer=self.oft_double_buffer,`
  (kwarg into memory-pool construction).
- Updated one docstring elsewhere in the file (`WHY THE active_idx
  CARVE-OUT IS EAGER-ONLY` block) that referenced ``--peft-double-buffer``
  descriptively (not part of the deprecation-alias handling itself) to say
  ``--oft-double-buffer`` -- this occurrence was NOT listed in the original
  scope brief; found via a repo-wide grep sweep after the listed edits.

### `python/sglang/srt/oft/staged_manager.py`
- Updated its one usage: `double_buffer=self.oft_double_buffer,` (reads the
  same `OFTManager`-inherited instance attribute; `StagedOFTManager`
  subclasses `OFTManager` and does not shadow this attribute anywhere else).

### `test/registered/unit/peft/test_peft_config.py`
- **Deviation from the literal brief** (see "Deviations" below): the shared
  `_args()` SimpleNamespace fixture previously hardcoded a single
  `peft_double_buffer=False` field. Since `validate_peft_args` now reads
  *both* `server_args.oft_double_buffer` and `server_args.peft_double_buffer`
  (for the OR-merge), a bare rename of that one hardcoded field to
  `oft_double_buffer=False` would have left the fixture without a
  `peft_double_buffer` attribute at all, and every one of the ~20 other
  tests using `_args()` would have hit `AttributeError:
  'SimpleNamespace' object has no attribute 'peft_double_buffer'` inside
  `validate_peft_args`. Instead, added `oft_double_buffer=False,
  peft_double_buffer=False` as new `_args()` keyword parameters (mirroring
  how `oft_target_modules`/`peft_target_modules` are already parametrized),
  and wired both into the `SimpleNamespace` construction.
- The real-`ServerArgs` regression test's `fields` dict (for the
  target-modules alias) similarly needed both `oft_double_buffer=False,
  peft_double_buffer=False` added (was a single hardcoded
  `peft_double_buffer=False` before).
- Added 3 new tests, immediately after
  `test_peft_target_modules_conflicting_with_oft_target_modules_is_rejected`:
  - `test_oft_double_buffer_alone_works_as_canonical_flag` -- `--oft-double-buffer`
    alone resolves `oft_double_buffer` to `True` (mirrors
    `test_oft_target_modules_alone_works_as_canonical_flag`).
  - `test_peft_double_buffer_deprecated_alias_still_works_and_warns` -- the
    deprecated flag alone still works, OR-merges to `True`, and logs the
    deprecation warning (mirrors
    `test_peft_target_modules_deprecated_alias_still_works_and_warns`).
  - `test_peft_double_buffer_alias_copy_survives_real_server_args_read_only_guard`
    -- the critical regression test, copying `7b75dc8a06`'s exact
    construction pattern (bare `ServerArgs.__new__(ServerArgs)`, fields
    populated via `object.__setattr__`, `_declarations_materialized = True`),
    adapted for this flag: drives `validate_peft_args` with only
    `--peft-double-buffer` set on a REAL, read-only `ServerArgs`, and asserts
    it does not raise `AttributeError` and resolves `oft_double_buffer` to
    `True`.
- Both `--oft-double-buffer`/`--peft-double-buffer` tests use
  `max_ofts_per_batch=3` (or `4` for the real-`ServerArgs` test), since
  `validate_peft_args` asserts `max_ofts_per_batch >= 3` whenever the
  resolved double-buffer flag is `True` (the default `max_ofts_per_batch=2`
  in `_args()` would otherwise trip that unrelated assertion).

## Deviations from the literal brief

1. **Test fixture needed BOTH fields, not a bare rename** (see the
   `test_peft_config.py` section above for the full mechanical reason): the
   brief said to "rename the `peft_double_buffer=False` kwargs... to
   `oft_double_buffer=False`" at the two named line numbers. Taken literally
   this breaks every other test using the shared `_args()` fixture
   (`AttributeError` on `server_args.peft_double_buffer` inside
   `validate_peft_args`, since the new OR-merge logic reads both fields).
   Fixed by adding both `oft_double_buffer` and `peft_double_buffer` as
   `_args()` parameters (mirroring the existing `oft_target_modules`/
   `peft_target_modules` parametrization) instead of a bare 1:1 rename.
   Verified: full suite passes (210/210).

2. **Two additional occurrences found beyond the brief's "11 occurrences
   across 5 files"**, via a repo-wide grep after finishing the listed edits:
   - `python/sglang/srt/oft/oft_manager.py` line ~880 (a docstring inside a
     different method, referencing `--peft-double-buffer` descriptively).
   - `test/registered/unit/oft/test_oft_moe_multi_tenancy.py` line ~936 (a
     test docstring, same kind of descriptive reference).
   Both are comments/docstrings, not code paths, and neither is part of the
   deprecation-alias handling -- they simply described ordinary
   double-buffer behavior by the flag's old name. Updated both to
   `--oft-double-buffer` for consistency with the rename (matches how the
   precedent commit `a2439d7fcd` updated non-deprecation comments/help-text
   referencing `--peft-target-modules` elsewhere in the same files).

Neither deviation changes any runtime behavior beyond what the brief asked
for -- both are corrections needed to keep the fixture/tests self-consistent
and to leave no stray old-name references outside the deliberately-kept
deprecation code.
